# StaySafe – Full Stack (React + Spring Boot + MySQL)

```
staysafe-fullstack/
├── docker-compose.yml        # optional MySQL container
├── backend/                  # Spring Boot 3 (Java 17, Maven)
│   └── src/main/java/com/staysafe/
│       ├── config/           # Security, JWT, CORS, DataSeeder
│       ├── controller/       # Auth, Property, Booking, Favorite, Notification, Ticket, Owner, Admin
│       ├── dto/              # request/response records + Mapper
│       ├── model/            # JPA entities
│       ├── repo/             # Spring Data repositories
│       ├── service/          # NotificationService
│       └── exception/        # ApiException + global handler
└── frontend/                 # React + Vite + Tailwind
    └── src/api/              # fetch client (JWT) + service functions
```

## 1. Start MySQL
Either use the container:
```bash
docker compose up -d
```
or your own MySQL 8 – then set `DB_USERNAME` / `DB_PASSWORD` (defaults: `root` / `root`).
The `staysafe` database and all tables are created automatically on first start.

## 2. Start the backend (port 8080)
```bash
cd backend
mvn spring-boot:run
```
Environment variables (all optional): `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET` (>= 32 chars), `CORS_ORIGINS`.

```bash

npm run dev
```
Vite proxies `/api` to `http://localhost:8080`. For production set `VITE_API_URL` (see `.env.example`).

## What works end to end
- Register / login with JWT, role-based access (Customer, Owner, Admin)
- Browse and filter verified listings, property details, reviews and ratings
- Date-based booking paid through Razorpay Checkout, cancellation with automatic refund (48h rule), receipts
- Favorites, support tickets (admin replies / resolves), profile editing
- Owner: add listings (go to admin review), incoming guests, earnings (10% platform fee)
- Admin: stats, approve / reject listings, ticket desk, **search any customer / owner / admin** (name, email, phone, ID + role filter), full user details, enable / disable, export to CSV / Excel
- Owner: **search customers who booked their properties** (name, email, phone, booking ID, property), view booking history, **export to CSV / Excel** (Excel has Customers + Bookings sheets)
- Real notifications generated by every action (polled every 30s)

## Room / flat / PG sharing
**Owners** (Add / Edit Property):
- *Who can stay*: gender (men only / women only / co-ed), food (pure veg / veg & non-veg), occupants (students / working professionals / both), plus smoking, alcohol, pets and visitors rules.
- *Room types*: any number of options per property (single, 2 / 3 / 4+ sharing, AC, attached bathroom), each with its own **price per bed**, total beds and beds open now. Property types: PG, Room (shared house), Flat, Co-living.
- *Residents* tab: add current residents / flatmates (name, age, occupation, college / company, food, habits, sleep schedule, bio). They are shown to prospective tenants as roommates only if the owner confirms the resident consented.

**Customers**:
- Filters on the listing page: sharing type, suitable for (men / women / co-ed), food, occupants, "only with beds available", plus the budget range.
- Each card / property page shows the rules as badges, the room options with beds left, and a **Roommates** tab (login required) listing residents and StaySafe members who chose to share their profile, with a compatibility % against your own profile.
- **Roommate profile** (Customer → Roommate Profile, or the prompt when booking): gender, date of birth, occupation, college / company, food preference, smoking / drinking, sleep schedule, languages, bio, and a consent switch for sharing with roommates.
- At booking the server checks the profile against the property's rules (gender, students / professionals, pure-veg, smoking, alcohol, age 18+) and shows the reasons if you are not eligible. Price comes from the chosen room option; one booking = one bed.

**Inventory**: a bed is taken when the payment is captured and given back on cancellation / full refund. If two customers pay for the last bed at the same time, the later one is refunded automatically. Roommate cards only expose first name + last initial, age group and lifestyle basics - never phone, email or exact age.

Listings created before this feature are migrated automatically (default rules + one "Standard room" at the old price); owners can edit them.

Demo (seed data): Priya (female, student, vegetarian) is eligible for **Green Valley PG** (women only) and **Skyline Apartments** (pure-veg flat) but not **Urban Nest** (working professionals only) or **Maple Residency** (men only, still under review).

## Razorpay payments (orders, checkout, verification, refunds, webhooks)

**Setup**
1. Create a Razorpay account and copy the **Test mode** API keys (Dashboard → Account & Settings → API Keys).
2. Start the backend with them:
   ```bash
   export RAZORPAY_KEY_ID=rzp_test_xxxxxxxx
   export RAZORPAY_KEY_SECRET=xxxxxxxxxxxxxxxx
   export RAZORPAY_WEBHOOK_SECRET=choose-a-long-random-string
   ```
3. Expose your local backend (webhooks need a public URL), e.g. `ngrok http 8080` or `cloudflared tunnel --url http://localhost:8080`.
4. Razorpay Dashboard → Settings → **Webhooks → Add new webhook**: URL `https://<your-tunnel>/api/payments/webhook`, secret = `RAZORPAY_WEBHOOK_SECRET`, and tick these events: `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid`, `refund.created`, `refund.processed`, `refund.failed`, `payment.dispute.created`, `payment.dispute.under_review`, `payment.dispute.action_required`, `payment.dispute.won`, `payment.dispute.lost`, `payment.dispute.closed`, `settlement.processed`.
5. Test cards / UPI: https://razorpay.com/docs/payments/payments/test-card-details/ (e.g. UPI id `success@razorpay`).

Without keys the app runs, but **booking returns "Razorpay is not configured"** – the old simulated payment was removed on purpose, so a booking can no longer be created without a captured payment.

**Flow**
1. `POST /api/payments/order` – server validates the stay, takes the price from the database and creates the Razorpay order.
2. The browser opens Razorpay Checkout (UPI, cards, netbanking, wallets).
3. `POST /api/payments/verify` – server checks the `razorpay_signature` (HMAC-SHA256, constant-time compare), **re-fetches the payment from Razorpay**, checks order + amount, captures it if it is only authorised, then creates the booking.
4. Webhooks drive the same state machine, so nothing is lost if the customer closes the tab after paying. A row lock on the payment guarantees one booking per payment even if verify and the webhook arrive together.

**Webhook endpoint** `POST /api/payments/webhook`: signature is verified over the **raw body** (`X-Razorpay-Signature`), every delivery is logged and de-duplicated by `X-Razorpay-Event-Id` (admin → Payments → *Webhook log*), failures return 5xx so Razorpay retries. Handled events:

| Event | Effect |
|---|---|
| `payment.authorized` | mark authorised, capture (if auto-capture is off) |
| `payment.captured`, `order.paid` | mark captured, create the booking if it does not exist yet |
| `payment.failed` | mark failed, notify the customer |
| `refund.created` / `refund.processed` | track refund, mark `REFUNDED` / `PARTIALLY_REFUNDED`, cancel the booking on a full refund, notify |
| `refund.failed` | reset refund, alert admins |
| `payment.dispute.*` (created, under_review, action_required, won, lost, closed) | record dispute status, alert admins (and the owner on creation) |
| `settlement.processed` | notify admins with amount + UTR |

**Refunds**: cancelling a booking (≥ 48 h before check-in) refunds the payment through Razorpay; if Razorpay rejects the refund the cancellation is rolled back. Admins can also refund fully or partially from the *Payments* tab.

Not included: owner payouts via Razorpay Route / RazorpayX (earnings shown in the owner console are calculated, not transferred). Bookings seeded as demo data have no Razorpay payment, so cancelling them refunds nothing.

## Photos & map location
- **Profile photo**: click your avatar (header banner of any dashboard, or Profile Settings for customers). `POST/DELETE /api/auth/me/avatar`.
- **Property photos**: owners upload up to 8 photos (drag & drop, first = cover) when adding or editing a listing. `POST /api/owner/uploads`.
- **Property location**: owners pin the property on an OpenStreetMap map (click, drag, address search or "use my location"); area + address are auto-filled from the pin. Guests see it in the new *Location* tab with an "Open in Google Maps" link. Editing the pin or area of a live listing sends it back for admin review; `PUT /api/owner/properties/{id}`.
- Images are validated by magic bytes (JPG / PNG / WebP only, 5 MB max, compressed in the browser first) and stored in `UPLOAD_DIR` (default `./uploads`), served from `GET /api/files/{name}`. Use S3 / GCS (replace `FileStorageService`) when you run more than one server.
- Map tiles and address search use OpenStreetMap / Nominatim, which are fine for development and light use; switch to a commercial tile + geocoding provider for production traffic.

## Owner KYC (CKYC + manual fallback)
Owners verify their identity right after registering (step 2 of sign-up), or later from the Owner Console:

1. **CKYC search** – owner picks an ID type (PAN, Aadhaar, Passport, Voter ID, Driving Licence), enters the number + date of birth and gives consent. 
2. **Found** – the CKYC record is shown; on confirm the server re-runs the lookup and marks KYC `VERIFIED` instantly.
3. **Not found** (or owner skips the search) – owner enters the government ID, name, DOB and address manually. It is format-validated (Aadhaar uses the Verhoeff checksum) and goes to the admin **KYC Review** tab (`PENDING_REVIEW`).
4. Owners can submit listings once KYC is `VERIFIED` or `PENDING_REVIEW`; **admins can only approve a listing when the owner's KYC is `VERIFIED`**.

Privacy: full ID numbers are never stored – only a masked value (`XXXX XXXX 1234`) and an HMAC hash (used to block the same ID on two accounts). Set `KYC_HASH_SECRET` in production. CKYC lookups are rate-limited (10 per 15 min per user).

**The CKYC registry is simulated.** The real registry (CERSAI) is only available to regulated entities / licensed KYC providers. `MockCkycClient` holds three demo identities; to go live, implement `CkycClient` with your provider and remove `@Component` from the mock.

## Notes
- Payment is simulated. To go live with Razorpay: add an endpoint that creates a Razorpay order, open Razorpay Checkout in `BookingPaymentView`, then verify the signature in `BookingController.create` and store the real payment id in `paymentRef`.
- Change `JWT_SECRET` and the seeded passwords before deploying.
- `spring.jpa.hibernate.ddl-auto=update` is convenient for development; use Flyway/Liquibase migrations in production.
